# Research: MES Parent-to-LMS Journey

## Decisions

### Fastify telemetry, request limits, and CORS

- **Decision**: Register `@fastify/otel` before application routes and initialize the OpenTelemetry SDK before constructing Fastify. Export telemetry to the console in local development, with an OTLP endpoint configurable for later environments; add low-cardinality business counters for the purchase, invitation, activation, and lesson-denial funnel. Never attach names, email addresses, invitation tokens, session IDs, or student IDs to metrics or spans. Register `@fastify/rate-limit` with a configured per-user request window: authenticated routes key by verified student ID, while public anonymous routes use the trusted client IP. Return the plugin's standard 429 response. Register `@fastify/cors` with an explicit environment-configured origin allowlist and credentials enabled only for approved origins.
- **Rationale**: The user explicitly requires these Fastify plugins and technical/business telemetry. `@fastify/otel` instruments Fastify request lifecycle and routes, while business funnel events need explicit counters. Local console export keeps the demo runnable without an observability service; the OTLP endpoint leaves a standard integration seam. Authenticated identity provides per-user limits, and IP fallback covers public pre-auth routes that have no user identity. Explicit origins and bounded metric attributes avoid widening browser access or exposing children's data and exploding metric cardinality.
- **Alternatives considered**: Keep telemetry as logs only or defer OpenTelemetry; use only IP-based limits for logged-in users; allow all CORS origins; add a collector/backend container to the demo. These either fail the explicit requirements, weaken user-level controls, create unsafe browser access, or add infrastructure beyond the mock's scope.
- **Operational details**: Window duration and request maximum are configuration, not hard-coded policy; select conservative local defaults and test that a limit is isolated per user and resets after the window. CORS development origins are explicit (including the Vite development origin); production defaults to the deployed web origin. Trust forwarded IP headers only when Fastify is configured behind the known reverse proxy.

### Distributed tracing across browser, API, and PostgreSQL

- **Decision**: Initialize a browser OpenTelemetry Web SDK before the React app, using fetch instrumentation and the W3C Trace Context propagator. Create checkout/onboarding action spans and inject `traceparent` (and `tracestate` when present) only to an explicit API-origin allowlist. Add those headers to CORS preflight allow-headers for configured web origins. Start the Node SDK before loading instrumented Fastify/`pg` modules; register Fastify instrumentation before routes and PostgreSQL instrumentation before the client is loaded. Keep one parent/child trace across browser, API, and database operations, and avoid duplicate server spans. Console span export is the local default; OTLP remains optional and no collector is deployed.
- **Rationale**: W3C trace context provides interoperable parent-child propagation. Web and Node SDKs are separate runtime environments; fetch instrumentation handles browser HTTP boundaries, Fastify instrumentation handles route spans, and PostgreSQL instrumentation supplies database child spans. Restricting header injection prevents trace metadata from leaking to third-party origins. The minimal console exporter preserves local reproducibility.
- **Privacy and correlation**: Add active `traceId`/`spanId` to allowlisted structured logs at log-write time. Use route templates instead of raw invitation URLs/query strings; exclude request/response bodies, raw errors, provider responses, secrets, student data, and sensitive SQL parameters. Never put secrets or personal data in baggage. A trace ID is diagnostic only. Checkout and later onboarding are separate traces; opaque internal purchase/invitation IDs may correlate them in trace links or allowlisted logs but never in metric labels. Use always-on sampling locally so validation captures complete traces; production deployments document a parent-based, ratio-sampling policy and finite trace retention before rollout.
- **Optional asynchronous boundary**: When T2 outbox/worker code is built, store only sanitized W3C trace context with the outbox event and extract it before processing. Ordinary near-term processing may continue the trace; delayed jobs/retries may create a new trace with a link to the originating span. Do not add a broker solely for tracing. This adapts OpenTelemetry messaging propagation guidance to a PostgreSQL outbox; it is not a PostgreSQL broker convention.
- **Alternatives considered**: Manually construct/parse trace headers, inject to all browser destinations, include IDs or tokens in baggage, or deploy a collector/alert stack now. Manual propagation risks invalid context, global injection leaks metadata, sensitive baggage violates privacy, and new telemetry infrastructure exceeds the mock scope.

### PostgreSQL read/write routing

- **Decision**: Retain `DATABASE_URL` as the primary/write target and add optional `DATABASE_READ_URL`, defaulting to `DATABASE_URL`; construct distinct read and write pools/interfaces. Local Compose supplies one PostgreSQL instance for both. Deployed environments may set the read URL to a replica. Route writes, transactions, checkout price/eligibility validation, enrollment authorization, and read-after-write flows to the primary. Route only explicitly lag-tolerant reads (such as catalog browsing and lesson content after authorization) through the read pool.
- **Rationale**: PostgreSQL hot standbys replay WAL asynchronously, so replica reads can be stale and can experience replay conflicts. Keeping authorization and consistency-sensitive reads on the primary preserves the next-request revocation guarantee and immediately visible onboarding/purchase outcomes. Separate interfaces permit later replica routing without requiring local replica infrastructure.
- **Operational behavior**: Do not silently reroute consistency-sensitive reads. A read-replica failure may return the existing recoverable dependency error; any future fallback to primary must be explicit, bounded, observable, and capacity-aware. Use the write pool for every transaction so a transaction cannot accidentally span primary and replica connections.
- **Alternatives considered**: Route all reads to replicas, use a replica for authorization, or synchronously wait for replica replay after each write. These respectively allow stale access decisions, violate the enrollment consistency policy, or add a replay-position protocol and latency beyond the small mock.

### Overall architecture

- **Decision**: Use the blueprint's modular monolith: React/Vite web client, Node.js/TypeScript/Fastify API, and PostgreSQL. Keep catalog, commerce, identity, and learning behind module service interfaces.
- **Rationale**: Matches the assignment's stack and time-box while keeping domain seams understandable without premature service extraction.
- **Alternatives considered**: Separate deployable services, Java backend, or a frontend-only simulation. Separate services add operational cost; the existing blueprint fixes the Node stack; a frontend-only flow cannot demonstrate server-enforced entitlements or transactional guarantees.

### Frontend styling

- **Decision**: Use Tailwind CSS in the React/Vite web client to style responsive purchase, onboarding, and LMS pages.
- **Rationale**: This is an explicit user preference and gives the small frontend a consistent utility-based styling approach without adding a component framework.
- **Alternatives considered**: Leave styling entirely to implementation choice or add a full component library; the former does not honor the clarified requirement, while the latter adds scope and dependencies not needed for this mock.

### TypeScript linting

- **Decision**: Configure and run typescript-eslint against the TypeScript source, with one documented repository lint command.
- **Rationale**: The repository has no existing linter configuration, and the user selected typescript-eslint for the TypeScript stack. A single linter keeps the check useful without duplicating overlapping tools.
- **Alternatives considered**: Leave the linter choice open or add multiple format/lint tools; the former does not honor the clarified choice, and the latter adds unnecessary setup for the time-boxed mock.

### Future event-driven processing and scale seams

- **Decision**: Keep the current modular monolith and its replaceable service interfaces. Add concise comments at real external-effect, retry, message-delivery, payment, and CPU-intensive boundaries to identify where asynchronous producers/workers could be introduced, and document those seams and future options in the README. Do not add a message broker or generic event framework for this mock.
- **Rationale**: This makes likely extraction points visible to a future implementation without spending the time-box on infrastructure or implying that a small demonstration is production-scale. No CPU-intensive workload is currently required; a worker is warranted only when such work exists.
- **Alternatives considered**: Add a broker/event bus now or create a generic worker abstraction without a current workload; both introduce operational and design complexity contrary to the stated scope. The optional T2 PostgreSQL outbox worker remains a concrete reliability slice for email delivery, not a broker-backed architecture.

### Checkout and idempotency

- **Decision**: Validate request shape and business eligibility before claiming an idempotency key, and cap the key at 255 characters. The frontend creates a new key for each user-initiated checkout and reuses it only for retries/double-clicks of that attempt. Persist the key with a canonical request hash. Same key/same request returns the stored outcome; same key/different request returns 422 (a project policy, not a Stripe guarantee). A duplicate request arriving while the first is still being processed receives a retryable 409. Mock payment is behind a `PaymentGateway`; successful confirmation creates paid order data, pending enrollments, invitations, and checked outbox inserts transactionally.
- **Rationale**: PostgreSQL `INSERT ... ON CONFLICT` gives an atomic insert-or-conflict decision for a unique key. Input validation before claiming prevents malformed input from consuming a key. Keying a new user attempt separately avoids replaying a prior failed outcome. Domain state and entitlements must not be committed on simulated payment failure.
- **Alternatives considered**: Trusting client prices, generating entitlements in the browser, or relying on an in-memory retry cache; these cannot enforce correctness across requests or processes. Do not hold a database transaction open over the payment call. Do not claim Stripe's exact replay/pruning semantics for this mock's local idempotency policy.

### Invitation redemption and activation

- **Decision**: Generate a high-entropy invitation secret, persist only its hash, and atomically claim an active, unexpired invitation with a conditional database update. Create the student and activate all enrollments for that student slot in the same transaction.
- **Rationale**: A conditional update with a single winner prevents concurrent double redemption; a student slot lets one onboarding activate the child's multiple purchased courses.
- **Alternatives considered**: Read-then-write checks, process-local locks, or one invitation per course; these permit races across processes or split one child's onboarding unnecessarily.

For invitation token rotation (T2 reminders), lock the invitation/slot state with `SELECT ... FOR UPDATE`
inside a short transaction before replacing the token. PostgreSQL row locks are held until the
transaction ends; do not rely on an unlocked read followed by an update.

### LMS authorization

- **Decision**: Install a global deny-by-default authentication guard. Only an explicit public allowlist may bypass it: course catalog, checkout, invitation read/activation, login, and health/readiness. Obtain student identity only from verified authenticated session state and check active enrollment from PostgreSQL for every LMS request; do not embed entitlement state in the session/JWT. Centralize lesson checks in one learning-module authorization function. Deny unentitled content without confirming resource existence.
- **Rationale**: Authorization must run on every request; a forgotten route must not silently become public. UI hiding is not access control; request identifiers are user-controlled. Re-reading enrollment state means revocation is effective on the next request rather than waiting for an embedded claim to expire.
- **Alternatives considered**: Frontend-only checks, ownership inferred from order lookup, or course access based only on successful login; none proves that the student is entitled to the requested lesson.

### Asynchronous email and reminders

- **Decision**: If T2 fits, write outbox records in the same transaction as their domain change and verify each expected insert succeeded before commit. Claim due rows with `FOR UPDATE SKIP LOCKED` in a short transaction, set `PROCESSING` plus a lease expiry (`locked_until`), commit, then call the email provider outside any transaction. Mark sent or schedule retry in another short transaction. Reclaim expired leases after worker crashes. Use a stable outbox row ID as a provider idempotency/message key where supported, dedupe keys for enqueueing, and idempotent handlers. Recheck invitation state at delivery time; reminder sends rotate and supersede links under a row lock. Delivery is at-least-once, not exactly-once; a rare duplicate email is accepted over silently lost mail. Do not rely on message ordering.
- **Rationale**: PostgreSQL row locks end with their transaction, while `SKIP LOCKED` skips currently locked rows only for that statement; a lease persists ownership across the provider call and enables crash recovery without holding a transaction over network I/O. The outbox prevents losing notifications after committed state. The mock can log email or use optional MailHog.
- **Alternatives considered**: Holding a transaction and row lock across email I/O wastes database connections and locks; marking sent before delivery can lose mail; adding a broker is unnecessary for the exercise's volume and time-box.

### Container startup and migrations

- **Decision**: Compose starts PostgreSQL and waits for its healthcheck, runs a one-shot migration-and-seed service, then starts API and optional worker only after migration completes successfully.
- **Rationale**: Container-running is not service-ready, and concurrent API/worker startup migrations can race. Compose dependency conditions express startup ordering and readiness/completion.
- **Alternatives considered**: Running migrations from every long-lived service at startup or depending only on container start; both permit concurrent migration or premature connection attempts. Startup dependencies do not guarantee ordering after later runtime restarts, so services still need recoverable connection handling.

### Test strategy and local validation

- **Decision**: In addition to business/security tests, write browser/API trace tests for valid W3C parent propagation, missing/invalid context creating a new root, DB child spans, CORS trace headers on approved origins, no trace-header injection to unapproved origins, and active trace/span IDs in allowlisted logs. Exercise log and trace sanitization with dummy secrets on failure paths. Unit-test pool selection so writes, transactions, checkout pricing/eligibility, enrollment authorization, and read-after-write use the primary; only explicitly stale-tolerant reads use the read pool. Use real PostgreSQL where guarantees rely on transactions, locks, or constraints. If T2 is implemented, add outbox context extraction/link tests. Validate the full journey from a disposable clean checkout with Docker Compose.
- **Rationale**: Mocks cannot prove database concurrency or transaction behavior; pool-routing tests must specifically prove that a lagging replica cannot authorize stale access. Browser and API spans require an end-to-end trace assertion rather than checking only that exporters emit data. A fresh-checkout run catches undocumented local dependencies.
- **Alternatives considered**: Unit tests alone or a numeric line-coverage threshold; neither is as meaningful as behavior-focused proof of the critical guarantees, and the feature spec does not define a coverage percentage.
